二、重点案例详解

1. FactoryPal：换线优化的对象应是“产品—产线—班次”组合

  • 来源链接：FactoryPal 客户案例
  • 所属行业：生活用纸；匿名客户，数据为供应商自报，未见独立审计。
  • 应用场景：多品种生产导致频繁换线；依赖人工试调，换线可达 28 分钟，不同班组表现不一致。
  • 核心做法：先进行 30 天诊断，收集跨班次表现；识别产线可持续的稳定速度和关键参数，按具体产品—产线组合给操作员实时建议，并持续根据新数据更新。
  • 使用技术：时序数据采集、参数推荐、闭环优化、操作员工作流嵌入；来源未披露具体模型和接口。
  • 可借鉴点：不要只训练一个“全线最优参数”模型；版型、BOM、设备状态、环境和班组必须共同进入上下文。推荐必须记录采纳、修改或拒绝原因。
  • 光伏工厂落地想法：针对换玻璃规格、胶膜类型、边框颜色或组件版型，建立历史“最后合格参数包”；换型前给出层压温度/真空时间、串焊温度/拉力、装框点胶等建议区间，并自动生成首件待确认清单。
  • 开发难度评估：中等。数据对齐和参数版本管理比模型本身更难。
  • 预期收益：换型时间、爬坡报废、首件等待时间下降；建议先以 20 次同类换型回放测算，不直接采用供应商的 33%。

2. UST：用“视频事件 + 物料身份”补齐换线过程盲区

  • 来源链接：UST VisionBox 案例
  • 所属行业：汽车零部件；匿名客户，发布时间未明确，访问于 2026-08-05。
  • 应用场景：非计划停机、换线中断、设备错位、原料放错位置或装错机台。
  • 核心做法：复用现有 CCTV 进行实时视觉分析；结合敏感传感器定位设备错位；给原料加智能标签，实现跟踪、识别和上机防错。
  • 使用技术：边缘视觉、目标/动作检测、传感器融合、RFID/智能标签、实时告警。
  • 可借鉴点：换线损失常发生在 MES 没有记录的微动作里。先定义“清线完成、物料核对、治具到位、参数下载、首件送检”五类事件，再决定摄像头是否值得接入。
  • 光伏工厂落地想法：在串焊和叠层换型区识别旧版型余料未清、焊带/胶膜批次不符、工装未复位；条码校验作为主判据，视觉只做补充证据。
  • 开发难度评估：中高。涉及现场摄像头角度、隐私、安全区和标签覆盖率。
  • 预期收益：供应商自报停机频次/时长降低近 35%、生产率提升 16%；本厂应以错料险情数、清线等待、换型后前 30 件 FPY 验证。

3. P&G：先解决模型怎样跨设备交付，再谈规模化 AI

  • 来源链接：P&G Azure IoT Operations 客户故事
  • 所属行业：全球消费品制造。
  • 应用场景：35 个以上国家的工厂设备新旧不一，单点 AI 试验可做，但难以一致部署、更新和回滚。
  • 核心做法：在云端构建 Kubernetes 应用/模型，通过 Azure Arc 编排到工厂边缘；以 MQTT 消息平面连接设备数据和事件驱动应用，保留适配不同设备的运行环境。
  • 使用技术：Kubernetes、Azure Arc、Azure IoT Operations、MQTT、边缘推理、DevOps。
  • 可借鉴点：把采集适配器、规则/模型、可视化和版本配置分层；模型包必须带输入字段契约、版本、适用设备和回滚方案。
  • 光伏工厂落地想法：将“换型参数核对器”做成只读边缘容器，同一代码通过配置适配不同品牌串焊机/层压机；异常时退回规则校验，不阻断 PLC。
  • 开发难度评估：高（平台化）；单产线 MVP 为中等。
  • 预期收益：来源称模型部署时间最多缩短 90%；对组件厂更现实的首期目标是一次应用升级从逐机操作变为集中发布，并把回滚控制在 15 分钟内。

4. Nisshin：实时平台的终点不是“有数据”，而是一线能自助使用

  • 来源链接：Nisshin Flour Milling 客户故事
  • 所属行业：面粉制造。
  • 应用场景：磨辊/筛网要随原料水分和硬度做微米级调整；既有实时系统技术门槛高，工厂难以自行扩展分析。
  • 核心做法：统一 IoT、PLC、MES、故障分析和核心系统数据，进行实时处理并在工厂屏幕展示；将预聚合、分析和可视化放到同一平台，已发布 100 多个跨部门看板，并逐步用机器学习数字化专家经验。
  • 使用技术：实时流处理、Fabric Real-Time Intelligence、Power BI、IoT/PLC/MES、机器学习。
  • 可借鉴点：工艺看板要绑定动作：谁确认、允许区间、越界如何升级、处理后如何验证，而不是只显示趋势。
  • 光伏工厂落地想法：建立“换型首件控制塔”，实时显示计划 BOM、实际上料、配方版本、设备状态、首件 EL/功率/拉力结果和未关闭项。
  • 开发难度评估：中等；已有 MES/数据湖时可明显降低。
  • 预期收益：减少 Excel 搬运和跨部门询问，提升首件放行可追溯性；量化目标应为取数工时、首件等待和跨班组参数偏差。

5. Sight Machine：排程应使用真实换线与爬坡时间

  • 来源链接：Sight Machine 与 Microsoft 客户故事
  • 所属行业：饮料制造；客户匿名，收益为案例方自报。
  • 应用场景：每周重排 10–15 次；静态平均速度和换线时间无法反映设备、清洗、物料和订单扰动。
  • 核心做法：数据层提供每 SKU 线速、实际换线/爬坡时长和实时状态；自然语言约束转换为混合整数规划（MIP），状态变化后重新求解，支持假设情景。
  • 使用技术：IT/OT 数据模型、MIP、自然语言到优化模型、预测分析、事件触发重排。
  • 可借鉴点：排程和换型优化应共用同一本事实账：实际开始/结束、合格首件时间、清线原因和参数稳定时间。
  • 光伏工厂落地想法：把“计划换型 20 分钟”替换成按版型转换对、班组、设备健康和待料状态预测的 P50/P90 时长；高风险换型预留质量确认窗口。
  • 开发难度评估：中高。
  • 预期收益：案例方称换线停机降低近 80%、爬坡延迟降低近 60%；本厂应先用历史回放评估交付、换型和在制品三项变化。

6. 韩国组件厂：七工序视觉框架提醒我们别把 EL 当孤岛

  • 来源链接：论文 DOI
  • 所属行业：光伏组件制造。
  • 应用场景：真实工厂的串焊、自动汇流、EL、层压、装框、边框和接线盒等七个环节存在图像质量信息，但常被分散使用。
  • 核心做法：以实际产线图像构建机器视觉质量框架，设计自动决策算法识别异常模式；论文报告 EL 和串焊环节缺陷检测准确率超过 95%。
  • 使用技术：机器视觉、图像分析、缺陷分类/决策；页面摘要未披露完整量产架构和持续监控方式。
  • 可借鉴点：跨工序图像必须用组件条码关联，并保留相机、配方、模型、光源和判定版本；仅看总体准确率不足，还要分缺陷种类统计漏放/误拒。
  • 光伏工厂落地想法：换型后前 30 件自动建立“首件视觉包”，对比串焊图、叠层定位、层后 EL、装框和接线盒外观，快速判断异常从哪道工序首次出现。
  • 开发难度评估：中高。
  • 预期收益：更快定位换型后缺陷起点，减少全线排查；论文准确率不能直接视为本厂上线指标。

7. 晶澳：全链追溯的目标是让工艺参数能解释最终性能

  • 来源链接：晶澳科技 2025 年度报告（第 28 页）
  • 所属行业：光伏电池与组件。
  • 应用场景：电池到组件的设备参数与最终性能难以完整关联，工艺窗口优化和异常根因诊断周期长。
  • 核心做法：规划“AI 生产线工艺参数预测模型与激光二维码全链追溯技术”，连接设备参数和最终性能，并支持虚拟量测、工艺窗口优化与根因分析。
  • 使用技术：激光二维码、全链数据关联、参数预测、虚拟量测、数字孪生。
  • 可借鉴点：先建立稳定的产品身份和参数版本链，再建模型；否则模型学到的只是错配数据。
  • 光伏工厂落地想法：首期只做一个版型的“换型证据包”：BOM 版本、上料批次、配方校验、首件结果、放行人和后续 30 件表现全关联。
  • 开发难度评估：高（全链）；限定一条线、一个版型的只读 MVP 为中等。
  • 预期收益：缩短异常取证与工艺窗口验证周期。项目仍处设计开发阶段，年报只写预期能力，没有披露量产收益。

四、结合光伏工厂的应用点子

点子 1：换型首件“数字证据包”

  • 痛点：首件放行信息散落在 MES、设备屏、纸质点检、EL 和聊天记录，异常后很难证明当时用了什么物料与配方。
  • 解决思路：以换型任务号为主键，自动汇总清线、BOM/批次、设备配方校验、关键动作、首件检验、放行人与后续 30 件结果；只读展示缺口。
  • 所需数据：工单/BOM、上料扫码、配方版本、设备事件、首件 EL/功率/尺寸/拉力、放行记录。
  • 技术方案：SQL/事件流 + 规则引擎 + Web 看板；可选用 Docling 解析旧 SOP，RAGFlow 提供有引用的问答。
  • 复杂度：中等。
  • 预期收益：首件等待和异常取证时间下降，错料/错配方风险更早暴露。

点子 2：换型爬坡曲线与“稳定点”识别

  • 痛点：换线结束通常以设备开机为准，但良率、节拍和参数真正稳定可能晚很多。
  • 解决思路：对换型后产量、节拍、关键参数与不良率做变点检测，定义“连续 N 件/分钟进入稳定区间”才算爬坡结束。
  • 所需数据：换型开始/结束、设备状态、节拍、报警、关键参数、缺陷和返工。
  • 技术方案：aeon/传统变点算法 + SPC + 可解释阈值；先离线回放，不联动设备。
  • 复杂度：中等。
  • 预期收益：得到真实换型损失，为排程和改善提供更可信的 P50/P90 时间。

点子 3：物料—配方双重防错校验器

  • 痛点：条码扫对了，但设备配方仍可能是上一版型；或配方正确、现场余料未清。
  • 解决思路：在首件前同时校验工单 BOM、实际批次、设备当前配方和换型清线事件；四者一致才显示“证据齐全”，不自动放行。
  • 所需数据：工单、BOM 替代料规则、物料扫码、配方读取、清线确认、例外审批。
  • 技术方案：规则引擎 + OPC UA/设备只读接口 + MES API + 审计日志；视觉仅用于确认余料/工装状态。
  • 复杂度：中等。
  • 预期收益：降低错料、错配方和未清线造成的批量风险。

点子 4：同类换型历史参数与异常检索

  • 痛点：工程师遇到爬坡异常时靠记忆找“上次怎么调”，难以跨班组复用。
  • 解决思路：按版型转换对、BOM、设备、环境和故障签名检索最相似的历史换型，展示当时参数、处置和后续质量；所有建议带原始记录链接。
  • 所需数据：换型台账、参数快照、报警序列、工艺变更、检验与处置记录。
  • 技术方案：结构化相似度 + 时序特征 + 文档 RAG；首期禁用自动参数写回。
  • 复杂度：中等。
  • 预期收益：缩短问题定位和交接时间，提高优秀班组经验复用率。

点子 5：边缘应用版本与健康台账

  • 痛点：视觉、采集和规则服务散落在工控机，版本不一致、异常重启和回滚依赖人工。
  • 解决思路：统一记录应用版本、配置哈希、设备适用范围、运行状态、资源占用和回滚包；先监控，不自动升级。
  • 所需数据：主机/容器清单、发布记录、日志、CPU/内存/磁盘、接口心跳。
  • 技术方案：容器化 + Git 版本 + Netdata/现有监控 + 灰度发布清单。
  • 复杂度：中高。
  • 预期收益：降低跨线复制成本，缩短边缘应用故障恢复时间。

五、今日最值得尝试的一个小项目

项目名称

换型首件“数字证据包”只读 MVP

推荐原因

它不要求先训练复杂模型，也不控制 PLC，却能同时改善换型效率、错料/错配方风险和异常追溯。更重要的是，它会生成后续优化模型最缺的高质量训练标签：一次换型到底用了什么、何时稳定、谁放行、后续质量如何。

MVP 范围

  • 选择一条组件线、一个高频版型转换对，覆盖最近 20–30 次换型。
  • 每次自动/半自动生成一张证据卡：工单与 BOM、物料批次、配方版本、清线完成、首件 5 项结果、放行签字、后续 30 件 FPY。
  • 红色只表示“证据缺失或不一致”，不自动停线、不自动放行、不写回 MES/PLC。
  • 支持按换型任务导出 HTML/PDF，异常复盘时可直接引用原始数据链接。

所需数据

工单与 BOM 版本、物料扫码/替代料审批、串焊机与层压机配方快照、换型事件时间戳、首件 EL/功率/尺寸/拉力/外观、放行记录、后续 30 件质量与返工结果。

实施步骤

  1. 第 1–2 天：字段与边界——选定版型转换对，确认 12–20 个必备字段、数据责任人和允许的人工补录项。
  2. 第 3–4 天：只读取数——用 SQL/API/CSV 对接工单、扫码、配方和检验数据；所有字段保留来源系统、时间戳和原始记录键。
  3. 第 5–6 天：规则与证据卡——实现 BOM/批次/配方一致性、清线先后顺序、首件结果完整性规则，并生成一页式证据卡。
  4. 第 7–8 天：历史回放——回放 20–30 次换型，和班组长逐条核对误报、漏项与例外审批。
  5. 第 9–10 天：影子运行——上线只读看板，记录证据齐套时间、人工补录量和异常命中，不改变现行放行流程。

周期与验收

  • 周期：10 个工作日。
  • 验收指标：历史换型字段自动齐套率 ≥ 85%；证据卡生成 ≤ 1 分钟；关键不一致规则经人工复核准确率 ≥ 90%；首件资料查找时间降低 ≥ 50%；0 次自动写回或自动放行。

扩展方向

第二阶段加入换型爬坡稳定点、同类历史检索和换型时间 P50/P90；第三阶段再评估参数区间推荐。任何参数推荐必须保留适用条件、来源记录、人工采纳结果和可回滚版本。

今日判断：最值得先建的不是“自动调参 AI”，而是可信的换型事实账。只有把物料、配方、动作、首件和后续质量连起来，AI 才能从漂亮演示变成可验证的工艺助手。
